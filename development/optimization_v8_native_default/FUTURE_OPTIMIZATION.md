# Reusable optimization practice after this packet

## Preserve an evidence-backed optimization ledger

For every candidate record: actual source/profile; observed bottleneck boundary; removable work/traffic; exact transformation; proof domain; cold preparation and recurring cost; layout; worker budget; raw before/after data; reviewer; accepted/declined/failing outcome and a concrete condition for reopening. A large kernel-only ratio is not a reopening reason for a known losing adapter.

The central lesson of B7 is that execution boundary matters: a fast leaf can lose when repeated initialization, producer layout and thread policy remain outside it. Do not replace this mistake with an unbounded fused kernel. Choose the smallest region that eliminates measurable expensive boundaries while preserving locality.

## Sequence for future work

1. Measure current accepted installed no-env behavior on actual packed data. Distinguish parent vs child, requested vs actual threads, build vs execute, fallback vs native work and nested vs disjoint stage times.
2. Find redundant complete work first: duplicates, unobserved diagnostics, immutable exact expressions, overly rich state, absorbing states and conservative bounds.
3. Treat producer layout and consumer schedule together. Direct final-layout production is usually a better hypothesis than adding a transpose and assuming SIMD compensates.
4. Separate dispatch granularity, cache microtile, logical domain and scientific resolution. Do not conflate them.
5. Test current backend with the same better layout before adding a dependency. Keep native value attributable beyond B.
6. Cache or recompute by measured cost. A 4-bit quotient cache may save decode CPU but consume additional RAM and reduce tile concurrency. A tiny table must preserve f64 accumulator semantics.
7. Widen to device-resident regions only when transfer+sync+capability+precision permit a genuine gain. All GPU claims remain distinct.
8. Package performance as a default policy with explicit scope. Users should not pay research setup costs or tune obscure knobs.
9. Freeze evidence before release, maintain small corruption/alias/tail/no-toolchain regressions, and keep expensive matrices manual until publication requires them.

## Useful residual metrics

Per region: total work units, actual native fraction, bytes decoded/materialized, source/hash reads, memory allocation count, dispatch count, microblock occupancy, register spill/vector lane utilization, f64 profile fraction, coefficient/classification cost, IO/checkpoint time, worker-tail time and thread contention. Collect high-cost counters only during diagnostics; uninstrumented total is the promotion baseline.

Rank candidates by removable end-to-end cost divided by implementation+proof+maintenance cost. A tiny native reducer improvement can be worthwhile as a building block, but must not delay a larger exact storage or batch improvement indefinitely.

## Known mistakes not to repeat

- Repeated `_ensure_loaded` source hash inside every block.
- Selecting from dense fallback profile for a packed production path.
- Treating 24 bands as 24 spatial tiles.
- Treating parent RSS as total resource demand.
- Treating build cache presence as proof the candidate kernel ran.
- Calling single-thread C under a parallel label a four-core comparison.
- Computing a new layout and then measuring the reducer without the pack.
- Replacing original double-intermediate addition with f32 coefficient lookup.
- Default enabling on one giant-block synthetic win.
- Shipping an opt-in source compiler path as a zero-DX default.
- Removing required validation or publication work to shorten the timer.
- Declaring cross-platform support from cross-compilation alone.

## Future interfaces

Keep semantic region contracts small and explicit, with a pure numerical core and separately owned runtime/IO. Stable private ABI layouts, source-bound artifacts, lifecycle leases and workload-eligibility certificates make future ISPC/Highway/Numba/GPU schedules comparable. Do not overbuild a plugin framework before two useful implementations exist.

A future change to public API, numeric tolerance, recovery/durability or automatic accelerator use requires its own versioned policy and review. The old negative evidence remains useful and should not be deleted when a new implementation succeeds.
