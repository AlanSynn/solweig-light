## Findings

1. **(minor, schedule at C6-70) Dossier-02 step-B scene matrix not fully covered.** Gate 1 uses two real scenes (35x32 reference, 96x96 dense motif). No negative-height, signed-zero, open/vegetated-extreme, or guarded-nonfinite variants appear in the owned evidence, so the clamp branch (`recipe.py:65`, trees in the fixtures are ≥0) and the exact-equality zeroing under nonfinite inputs have no direct three-way parity run. Mitigation: `normalize` is line-for-line the removed `service._producer` body (compared statement-by-statement), and census C6-02 independently proved route A ≡ route B; `test_recipe_parity.py` calls the *installed* `service._producer`, so once C6-70 applies the diff the parity test must be re-run to keep covering route A. Low residual risk, but the gap should be closed, not assumed.
2. **(minor, schedule at C6-70) Census step-E differential proof is partially delivered.** The census T3 note permits dropping `standalone_implementation` "only after C6-10 centralizes normalization, WITH dossier step-E differential proof". Centralization is proven (verification 1). The delivered step-E subset covers: corrupt array payload, corrupt visibility sidecar, forged manifest, and one source-content perturbation (Trees). Dossier step E also lists: metadata perturbation (geotransform/projection), DEM/DSM content perturbation, patch-table/profile/implementation perturbation → confirm misses, input mutation during preparation, simultaneous readers/producers, and overwrite=False failures. Not all are covered. Implementation-perturbation rekey follows mechanically from the fingerprint closure (verified present in the identity), and concurrency/overwrite semantics are store-level code the candidate does not touch — but the census's stated condition is the full step-E matrix, so the remainder is owed at C6-70.
3. **(nit) Dead code and a triplicated name tuple in the post-image.** After integration: `svf_calculator_compact` import (`service.py:22`) and `RESULT_NAMES` (`service.py:25`) become unused in `service.py` (base used them only inside `_producer`, `git show 01092950` lines 21/24/82/83); the pipeline post-image leaves the module-level alias `svf_calculator` (`pipeline.py:22`) unused. The 19-name sequence now lives in `recipe.py:49-51`, `service.py:25`, and `pipeline.py:32-33` (plus the store's `SVF_FIELDS`); `recipe.py:133`'s `zip` trusts `svf.py`'s return order blindly (truncates silently on drift). The parity test's `len==19` + name-set assertion would catch most drift. Cosmetic/robustness only.
4. **(observation, pre-existing, not a C6-10 defect) Identity keys are path-instance-specific.** Base `raster_fingerprint` captures all GDAL metadata domains including `DERIVED_SUBDATASETS`, whose strings embed the **absolute file path** (`cache/geometry.py:80,96`). I verified: byte-identical scenes built at two directories produce different identity `inputs` and hence different digests/keys; this fully explains why the candidate's recorded keys (e.g. `7998d95e…`) and my re-run's keys differ while all invariants hold. Consequences: (a) recorded literal keys in C6-10 evidence are not reproducible across directories/machines — only within-run invariants are meaningful; (b) a native cache root shared across different preprocessing directories would never hit across dirs (census warm reuse is within one dir, unaffected). Recording for C6-70 awareness; out of C6-10 scope.
5. **(observation) Guard semantics slightly strengthened, manifest identity reshaped — both safe.** `guarded_producer` checks inputs before *and* after production; the old pipeline producer checked only after (fail-fast change only, same `InputChangedError` contract). The standalone manifest identity changes shape (wraps `numerical_recipe.digest` instead of inlining input fingerprints); digest binds the input fingerprints, and the e2e exercised export/compare paths with bitwise-equal artifacts.

One early `git apply` landed in the shared main-repo checkout due to shell cwd reset; it was reverted immediately and the shared src verified clean (`git status` shows only the pre-existing untracked `optimization_v4/`, `optimization_v5_claude/`, `optimization_v6_continue/`, none mine).
