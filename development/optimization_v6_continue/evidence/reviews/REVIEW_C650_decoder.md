## Claim-by-claim verification

### 1. Precedence exactness — VERIFIED (source + empirically)

The claimed original order is the ACTUAL order in the base source:

- `visibility_compiled.py:127-143` (`decode_block`): per channel — owners acquired and `_check_open()`ed in stable sorted-by-id order (`:133-137`), then per-leaf interval checks in leaf order (`:138-140`), then the native `_decode`, whose reserved scan runs patch-major/pixel-inner and raises `IndexError('Reserved visibility code')` mid-loop (`:17-35`). For the lazy pair, `_decode_diff` (`:84-87`) decodes the shadow leaf first, vegetation second, then subtracts in place.
- Consumer sequence `patch_radiation.py:119-128`: sh -> vs -> vb -> `diff_from_shared_decoded` (its own open/range checks, `visibility_compiled.py:162-169`) -> else direct `_block(diffuse)`; longwave triple at `patch_radiation.py:896-897` in the order shmat, vegshmat, vbshvegshmat.

The prepared implementation reproduces this by interleaving, not hoisting: `visibility_prepared.py:201-214` — all locks first (globally sorted by id, `:336-340`), then per slot in demand order: `owner._check_open()` per owner (slot owners sorted by id, `:258`), per-leaf interval checks (`:210-212`), then `_preflight` per fresh stream (`:213-214`), with `_preflight` (`:80-93`) scanning in `_decode`'s exact patch-major/pixel-inner order and skipping mode 4 exactly as `_decode` does. Cross-channel precedence (earlier channel's reserved discovery before a later channel's open/range error) therefore holds. `test_error_precedence.py` is 17 test items (16 functions + 2 parametrized cases); the prepared-path (not fallback) cross-channel proofs are the all-owners-open cases at `test_error_precedence.py:59-68` (reserved-in-shadow vs range-in-building) and `:71-77` (range-in-shadow vs reserved-in-vegetation), plus the longwave reserved-before-closed-building case at `:197-200`. Baselines are the real consumer functions (`conftest.py:116-127`), with type AND message asserted (`:42-44`).

**Worker's notable v5-fused claim — CONFIRMED, and it is a real latent divergence.** Source: `_fused_guard` (`patch_radiation.py:160-175`) runs ALL leaves' open and range checks before any preflight (`:200-206`), so the fused route reorders checkpoints across channels. Empirically (my probe, 16-pixel scene, reserved code in shadow, vegetation owner closed, 5 consistent patches):

- retained `_shortwave_visibility_blocks` and the full `Kside_veg_v2022a` entry: `IndexError('Reserved visibility code')`;
- same entry with `SOLWEIG_LIGHT_FUSED_RAD=1`: `RuntimeError('Native visibility is closed')`.

The prepared route is exact in this corner (decline+fallback when the closed owner blocks admission — probe showed the drop-in returning `None`; interleaved preflight when all owners are open — tests above). This v5 divergence deserves a line in the v5 known-divergences record; default-off env gating means it only manifests for fused-route users who also hold closed owners and reserved payloads.

### 5. Closed-owner safety — VERIFIED

So a closed owner can never present a borrowable descriptor; `_build_slot` additionally declines on `getattr(owner, 'closed', False)` when no cache exists (`visibility_prepared.py:271-277`), the documented belt-and-suspenders. Tests: `test_prepared_decode_reports_closed_owner_at_open_checkpoint` (`test_error_precedence.py:205-226`) and `test_close_lifetime.py:31-44, 99-113`.

## Findings

1. **[Note — inherited, not a candidate defect] Whole-process pytest collection collision.** Running `pytest tests/optimization_v5/radiation/test_p01_fused_blocks.py tests/optimization_v6/decoder/` in ONE process fails at collection: both trees' test modules do bare `from conftest import ...`, and one directory's `conftest` module wins `sys.modules`, so the other's import misses names (observed: `cannot import name 'assert_fields_bitwise' from 'conftest' (tests/optimization_v6/decoder/conftest.py)`). I reproduced the identical failure on my clean review tree at 99681b53 WITHOUT the decoder work (`v5/radiation + v6/cylinder_sw`), so this is a pre-existing repo-wide test-layout limitation the candidate inherits, not introduces. Per-directory runs (the documented workflow) are unaffected; both suites pass individually. Recommend the integrator keep per-dir invocation or adopt package `__init__.py`/unique conftest names tree-wide.
2. **[Note — documented semantics, concurrent callers only] Lock-hold window differs from the original.** Prepared decode holds every involved owner's lock for the whole combined decode (`visibility_prepared.py:45-53`); the original releases each channel's lock between channel decodes. A concurrent `close()` of a LATER channel's owner during an EARLIER channel's decode raises `RuntimeError` in the original but blocks until the combined decode finishes in prepared (which then succeeds). Both outcomes lie within the original's own race-dependent outcome set; serial callers see identical results and error timing. This is the established `_fused_guard` convention and is explicitly documented in the module docstring. `test_close_lifetime.py:47-81` honestly asserts both admissible end states rather than a fixed one.
3. **[Note — doc imprecision] Buffer-contract error ordering.** `integration_recipe.md` says buffer-contract violations raise "before any lock is taken" — true for the count/dtype/flags checks (`visibility_prepared.py:192-200`) but not for the shape check, which raises under the locks and AFTER the original checkpoints (`:220-223`). The late order is actually the correct choice (an original IndexError/RuntimeError outranks the new-API ValueError, so no original checkpoint is masked — consistent with `test_fallback.py:107-126`, which only exercises clean payloads). Recipe wording should say "count/dtype/flags before locks; shape after the original checkpoints".
4. **[Note — deliberate admission gap] Lazy base channels always fall back.** `decode_block` admits a `LazyDiffVisibility` base channel over packed leaves (`visibility_compiled.py:129`), but `prepare_channels` declines any lazy base channel (`visibility_prepared.py:320`). Such demands are exact (full fallback) but get no acceleration. Documented in the module docstring as intentional ("the pipeline never produces one"); recorded here so the integrator knows the prepared route's admission is strictly narrower than `decode_block`'s for base channels.
5. **[Note — comment arithmetic] `test_no_hidden_copy.py:103`.** The comment says a decoded-shadow copy "would be rows*patches*4 = 393216 bytes here"; with BLOCK_ROWS=64 and 153 patches the true figure is 64*153*4 = 39168 bytes — which is exactly the assertion bound on line 105. The assertion itself is correct and load-bearing (a 39168-byte copy plus dispatch overhead exceeds it); only the comment's number is wrong (it does not correspond to any rows/patches combination in the test).
6. **[Confirmed for the record] v5 fused reserved-vs-later-error divergence.** As detailed under claim 1: `SOLWEIG_LIGHT_FUSED_RAD=1` + reserved code in an earlier channel + closed later-channel owner yields `RuntimeError('Native visibility is closed')` where the retained route yields `IndexError('Reserved visibility code')`; root cause `_fused_guard` hoists all open/range checks ahead of all preflights (`patch_radiation.py:160-175` vs `:200-206`). The prepared route is exact in this corner. Recommend recording this in the v5 known-divergences list (it is latent, not new).
